## 상태와 저장 모델

`DiaryDraft`는 이름·기록 방식·제본·대표 색상·사용자 sRGB 색상·표지 스타일·속지·방향을 가진 생성 화면 상태입니다. 기존 열거형을 그대로 재사용합니다. 기록 방식과 제본은 독립 속성입니다. `DiarySummary`는 표시용 투영이며 저장하지 않습니다.

`DiaryDocument`는 UI와 SwiftData 매크로에서 분리한 Codable 값 타입입니다.

| 속성 | 의미 |
|---|---|
| id | 생성 시 UUID, 제목과 무관한 안정적인 문서 식별자 |
| title | 앞뒤 공백 제거한 필수 이름 |
| options | 선택한 기존 DiaryDraft의 스냅샷, 이름도 정규화 |
| createdAt / updatedAt | 절대 시각 Date, 최초 생성 시 동일 |
| pages | 순서를 유지하는 DiaryPage 배열, 최초 1개 |

`DiaryPage`는 UUID `id`, 부모 UUID `diaryID`, `paper`, `orientation`, `widthMM`, `heightMM`, 선택적 `date`를 가집니다. A4 세로는 210×297mm, 가로는 297×210mm입니다. 방향·속지는 생성 옵션을 복사합니다. 페이지 UUID를 향후 필기·이미지·스티커 연결 기준으로 사용할 수 있지만 개체·레이어 스키마는 아직 구현하지 않습니다.

날짜형 최초 페이지의 `DiaryDate`는 생성 시 기기 시간대로 계산한 그레고리력 연·월·일입니다. 이후 시간대가 바뀌어도 날짜가 변하지 않습니다. 날짜에 고유성 제약을 두지 않아 동일 날짜에 여러 페이지를 연결할 수 있습니다. 자유 기록형·스크랩북의 날짜는 nil입니다. 페이지 추가·재정렬 API/UI는 후속 범위입니다.

## 영구 저장

SwiftData `StoredDiary`는 고유 UUID, `formatVersion = 1`, JSON `documentData`를 저장합니다. JSON은 SwiftData 행 내부의 문서 데이터이며 별도 JSON 파일 저장소가 아닙니다. 문서와 초기 페이지 전체를 한 트랜잭션으로 확정하며 autosave는 끕니다. 저장 오류는 rollback하고 목록에 추가하지 않습니다. 전용 ModelContext를 사용해 View의 변경과 분리합니다. CloudKit 연결은 명시적으로 `.none`입니다.

불러올 때 버전·JSON 디코딩·문서/행 ID 일치·최소 한 페이지·중복 페이지 ID·부모 ID·양수 크기·필수 이름을 확인합니다. 하나라도 읽지 못하면 정상 빈 목록으로 처리하지 않고 오류와 재시도를 표시하며 생성도 막습니다. 원본 DB를 삭제하거나 새 빈 DB로 교체하지 않습니다.

기존 버전은 사용자 데이터를 저장하지 않았으므로 기존 사용자 저장소의 마이그레이션은 없습니다. 샘플은 가져오지 않습니다. 이후 SwiftData 스키마 또는 JSON 구조 변경 시 버전과 명시적인 마이그레이션을 설계해야 합니다. 지원하지 않는 문서 버전은 거부합니다. 현재 JSON 전체를 갱신하는 방식은 대용량 필기·미디어에는 적합하지 않으므로 편집기 단계에서 별도 저장 구조를 검토해야 합니다.

## 원본과 범위 차이

Notion 모델은 명시적으로 도메인 제안 초안입니다. 문서/페이지 UUID와 날짜·크기·방향 개념은 참고하되 상품·권한·소유 계정·휴지통·동기화 필드는 구현하지 않았습니다. 이번 요청이 로그인 없는 로컬 저장으로 범위를 정했으므로 원본 기능 초안 SAVE-01의 로그인 요구는 이번 단계에 적용하지 않습니다. 초기 1페이지·A4·현지 오늘 날짜는 이번 대화에서 사용자 승인된 사항이며 원본의 기존 확정 정책으로 표기하지 않습니다.

기술 선택 근거는 [ADR-003](decisions.md#adr-003--swiftdata-문서-저장과-생성-완료-경계)를 참고합니다. 백업·동기화 구현 시 안정적인 UUID와 날짜를 유지하고 포맷 버전·충돌·에셋 참조 정책을 별도 설계해야 합니다.
