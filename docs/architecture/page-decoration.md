## 기존 데이터와 저장 경계

기준 main `fb1f45d`에 5차 PR #6이 병합된 것을 GitHub API와 커밋 이력으로 확인했습니다. 기존 SwiftData `StoredDiary` 스키마, `FolinaLocal`, formatVersion=1, 문서·페이지 UUID와 PencilKit 경로를 유지합니다. 문서 JSON에 선택적 `deletedPages`만 추가하며 누락/null은 빈 휴지통입니다. 기존 파일을 이동·삭제하거나 빈 저장소로 초기화하지 않습니다. 호환성 범위는 구버전 → 신버전입니다. 구버전 앱으로 재저장하면 새 필드가 소실될 수 있으므로 다운그레이드 후 보존을 보장하지 않습니다.

문서의 `pages` 배열은 활성 페이지 순서, `TrashedDiaryPage`는 페이지 원본·삭제 전 위치·책갈피 여부·삭제 시각입니다. 페이지 정렬은 UUID 순열만 허용합니다. 마지막 활성 페이지 삭제는 UI와 모델 모두에서 거부합니다. 기존 0페이지 문서는 오류 없이 읽고 페이지 관리에서 추가할 수 있습니다.

`DiaryRepository.updatePages`는 새 ModelContext에서 최신 확정 문서를 읽고 화면의 기대 문서와 비교한 뒤 한 트랜잭션으로 변경합니다. 오래된 문서는 덮어쓰지 않고 재로딩을 요청합니다. 페이지 작업 실패 시 목록을 성공 상태로 바꾸지 않습니다. 책갈피도 새 context에서 현재 JSON의 해당 집합만 변경하므로 페이지 관리 결과를 오래된 값으로 덮어쓰지 않습니다. 페이지 관리 중에는 UI 요청을 직렬화합니다.

## 추가·복제·정렬·휴지통

- 추가: 다이어리 기본 속지·방향으로 A4 페이지를 생성하고 새 UUID로 배열 끝에 저장한 뒤 이동합니다. 날짜형은 기기 현지 오늘, 나머지는 날짜 없음입니다. 기존 생성 정책을 재사용하며 기존 페이지 날짜는 바꾸지 않습니다.
- 복제: 원본 바로 다음에 새 UUID의 페이지를 추가합니다. 속지·크기·방향·날짜와 저장 좌표를 유지합니다. 필기는 새 페이지 파일에 원본 payload를 복사하고, 객체는 새 객체 UUID·새 페이지 UUID로 복사합니다. 책갈피는 원본에 유지하며 복제 페이지에는 자동 부여하지 않습니다.
- 정렬: 페이지 관리 목록의 이동 핸들로 드래그합니다. 순서만 변경하고 필기·객체·사진 연결은 UUID로 유지합니다.
- 삭제: 확인 후 휴지통으로 이동합니다. 활성 책갈피에서 제거하되 복원용 여부를 보관합니다. 모든 필기·꾸미기·사진 파일은 유지합니다.
- 복원: 같은 UUID로 원래 인덱스에 삽입합니다. 앞 페이지가 줄었으면 배열 끝에 삽입하며, 이전 책갈피를 복구합니다. 읽던 페이지가 삭제되면 남은 첫 페이지를 선택합니다.

이번에는 영구 삭제·휴지통 비우기·참조 파일 가비지 수집 UI를 제공하지 않습니다. 원본의 수동 비우기 정책을 영구 삭제로 대체하지 않고 안전하게 보관합니다. 저장 용량 회수는 후속 기능입니다.

## 객체·사진 형식

`PageDecoration`은 version=1, diaryID, pageID, width, height, objects를 가진 페이지별 JSON입니다. `PageObject`는 id, pageID, kind(text/photo), text, fontName, fontSize, RGBA color, 선택적 assetID, photoStyle, 중심 x/y, width/height, rotation(도), zIndex를 저장합니다. 현재 기본 시스템 글꼴만 제공합니다. 텍스트는 한글·줄바꿈을 포함하는 원본 문자열이며 래스터 이미지로 합치지 않습니다.

사진 원본은 앱 내부의 UUID 파일이며 배치 정보에는 절대 경로 대신 assetID만 저장합니다. PhotosPicker의 이미지 단일 선택을 사용하며 전체 보관함 권한을 요청하지 않습니다. 사진은 전달받은 데이터가 디코딩되는지 확인한 후 내부 파일을 원자적으로 확정하고 객체 참조를 저장합니다. 전달받은 원본 바이트는 수정하지 않습니다. 보관함 사진 삭제 후에도 내부 파일을 사용합니다. 표시만 ImageIO의 최대 2048픽셀 썸네일로 디코딩합니다.

일반·폴라로이드·종이 코너는 photoStyle에 저장하고 화면에서 합성합니다. 사진 확대·회전·프레임 변경은 원본 파일을 변경하지 않습니다. 복제 페이지는 같은 immutable assetID를 공유합니다. 객체 삭제·페이지 휴지통 이동 시 파일을 지우지 않으므로 다른 복제본의 사진이 사라지지 않습니다.

### 파일 위치

- 기존 필기: `Application Support/FolinaInk/v1/<diary UUID>/<page UUID>.json`
- 꾸미기: `Application Support/FolinaDecoration/v1/<diary UUID>/pages/<page UUID>.json`
- 사진: `Application Support/FolinaDecoration/v1/<diary UUID>/assets/<asset UUID>`
- 충돌 사본: 각 저장소의 `<diary UUID>/conflicts/<page UUID>-<새 UUID>.json`

복제 sidecar/사진 파일을 먼저 준비한 뒤 DB에서 새 페이지 참조를 확정합니다. 중간 실패는 원본을 건드리지 않으며 참조되지 않는 파일이 남을 수 있습니다. 사진 삽입 후 객체 저장 실패도 같은 원칙입니다. DB와 파일 저장소 전체가 하나의 원자적 트랜잭션이라는 보장은 없습니다. 실패 파일의 자동 삭제는 보존 안전성을 위해 하지 않습니다.

## 자동 저장과 충돌 보호·복구

필기와 꾸미기는 각자 400ms 디바운스, 저장 요청 직렬화, 읽기 복귀 및 앱 비활성 시 flush를 사용합니다. 각 저장소 actor에서 마지막으로 읽거나 성공적으로 저장한 값과 디스크 현재 값을 비교합니다. 두 값이 다르면 확정 파일을 유지하고 이번 입력을 UUID 보호 사본 파일로 원자 저장한 뒤 충돌로 표시합니다. 보호 사본 기록까지 실패하면 일반 저장 실패로 처리하고 편집 화면을 유지합니다. 문서/페이지 불러오기 실패나 손상 파일은 빈 데이터로 덮어쓰지 않습니다.

현재 변경 revision까지 성공 저장 또는 보호 사본 기록이 확인된 경우에만 읽기로 돌아갈 수 있습니다. 그 이후 다시 편집한 메모리 변경에는 새 저장 확인이 필요합니다. 일반 저장 실패 시 메모리 입력을 유지하며 재시도합니다. 보호 사본은 페이지 관리에서 열람하고 **기존 페이지를 덮어쓰지 않는 새 페이지**로 복구합니다. 선택한 종류(필기/꾸미기)의 사본과 현재 원본 페이지의 다른 종류 콘텐츠를 조합합니다. 종류별 사본은 서로 다른 시점일 수 있으며 두 파일의 동일 시점 통합 스냅샷은 보장하지 않습니다. 복구 후에도 사본을 삭제하지 않습니다.

비교·쓰기 보호는 앱 내부의 공유 actor와 MainActor 경계에 대한 단일 프로세스 로컬 보호입니다. 외부 클라우드/공동 편집/별도 프로세스의 동시 쓰기 잠금은 구현하지 않습니다. 쓰기 도중 종료는 원자 파일 교체로 기존 확정본을 보호하지만, 성공 저장·보호 사본 확정 이전의 마지막 입력과 강제 종료 시 메모리 변경은 보존을 보장하지 않습니다. 다이어리 전체 백업은 DB·필기·꾸미기·사진·보호 사본을 함께 포함해야 합니다.

## 공통 좌표와 표시 순서

기존 필기 좌표를 재사용합니다. 1mm=4 논리 단위이며 기존 필기 파일이 있으면 그 width/height를 기준으로 꾸미기를 초기화합니다. 꾸미기 재로딩 시 두 좌표 크기가 다르면 재해석하지 않고 오류로 막습니다. 페이지 크기 변경 UI는 이번 범위 밖입니다.

표시 순서는 **속지 → 필기 → 텍스트·사진(zIndex) → 선택 표시**입니다. ‘앞으로/뒤로’는 텍스트·사진 객체 사이의 한 단계 이동입니다. 고급 레이어 패널이나 필기와 객체 사이의 자유 재정렬은 제공하지 않습니다. 읽기와 편집은 같은 `PageObjectVisual`과 페이지 좌표를 사용합니다. 회전/확대/창 크기는 표시 배율만 변경하고 저장 좌표를 바꾸지 않습니다.

객체 중심이 음수이거나 종이 범위를 넘어도 좌표를 잘라 저장하지 않습니다. 종이 경계의 표시만 clip하고, 전체가 종이 밖인 객체도 선택 도구의 객체 목록에서 선택하거나 ‘가운데로’로 명시적으로 이동할 수 있습니다. 이 버튼을 누르기 전에는 자동 위치 보정하지 않습니다.
